ETL Copilot

A test-gated build runbook for an agent that helps data engineers get a clean dataset: it profiles a raw CSV, drafts a Glue ETL job, gets the engineer's sign-off, runs and validates it, then writes the docs. Built from scratch on Strands + Bedrock AgentCore.

Scope CSV only — no PDF/JSON ETL Glue Python Shell (not Spark) Data 2–3 quirky datasets Rules 3–5 quality checks Pipeline first · UI last Region us-west-2
Architecture Console UI Phase 0 · Setup Phase 1 · Plumbing Phase 2 · IAM Phase 3 · Agent Phase 4 · Scale Phase 5 · UI Done
Rule of the runbook

Do the steps in order and do not advance past a step until its Test Gate passes. The internal pipeline (Phases 0–4) is built and proven end-to-end first; the Console UI (Phase 5) is layered on last, once the pipeline works completely on its own.

Reference

Architecture & who does what

Data flows left to right; the only place it stops is the human gate. Everything that costs money or moves data sits behind one agent with one narrow IAM role — that boundary is your primary safety control.

Input

  • CSV lands in the S3 landing/ prefix (later: uploaded via the Console)
  • 2–3 datasets, each with a deliberate quirk: mixed date formats, ragged nulls, a PII column, mixed types in one field
  • Fixed target rules: no nulls in key columns, valid date range, no duplicate IDs

Process · autonomous, human-gated

  • Supervisor sequences the run itself — no manual step-by-step driving
  • Profiler summarizes the mess; Script Writer drafts a Python Shell ETL script
  • Draft is proposed, not run → human approves before any write
  • Execution Agent runs the job → polls status → Athena validation
  • Fail → revise → re-approve → re-run (loop)
  • User can steer by chat; Supervisor routes the note to the right agent

Output

  • Cleaned, partitioned Parquet in staging/
  • The approved ETL script, versioned
  • Markdown data dictionary + quality report
  • First-run success rate across the 2–3 datasets

Safety

Start with the 3 Core agents (Supervisor + Script Writer + Execution Agent) using the Strands agents-as-tools pattern (sub-agents wrapped as @tools). Add Profiler and Documenter as separate agents only if Phase 3 finishes early — a 5-agent split is more than the timeline needs to prove the idea.

Design target · built in Phase 5

The Copilot Console

Not a wizard — a conversation. The user's only job is to upload one CSV; the agents then run the pipeline autonomously and narrate each step in plain bullets. A chat box stays open the whole time, so the user can set or change preferences — "that's a SKU, not PII" — and the Supervisor routes the note to the right agent and revises before the next step. The only thing that ever waits for a human is the approval gate before data is written.

Not yet

This is the design target, not a build task for now. The UI is the last thing built (Phase 5) — only once the internal pipeline runs end-to-end on its own. The mockup below is a static illustration of the intended interface, not a working front-end.

What the person actually does

01 · UPLOAD

Drop a CSV — that's it

The only manual action. CSV-only at the door; the run drives itself from there, no step buttons to press.

02 · WATCH

Read the narration

After each step, the responsible agent posts a plain-language bullet summary of what it just did — legible work, not a spinner.

03 · STEER

Chat to set preferences

Type a correction any time; the Supervisor routes it to the right agent and revises the plan before the next step.

04 · CLARIFY

Answer in one tap

When the agent is unsure it flags it with quick-select options — it never guesses silently or blocks waiting for free text.

05 · DECIDE

Approve one plan

The single gate: a plain-English summary (full script collapsed) that already reflects your preferences.

06 · KEEP

Collect the outputs

Data dictionary, quality report, and the staging location of the cleaned Parquet — with a recorded approval.

A useful use case

Persona · Maya, a data engineer onboarding a new vendor feed

Every week a new SaaS vendor drops a customers.csv export into a shared bucket. The dates come in two formats, one column is raw PII, and about one row in ten is missing a country. Today Maya hand-writes a cleaning script, runs it, eyeballs the output, and hopes she caught everything — an hour she can't easily hand off or audit later.

With the Console she drops the file and does nothing else. The Supervisor profiles it, flags the email as likely PII, and drafts the fix — narrating each step in bullets. Mid-run she realizes that "email" column is actually a hashed partner ID, so she types "that's a SKU, not PII." The Supervisor reroutes to the Script Writer, shows a diff dropping the mask, and the approval card updates to reflect her note. She approves once; it runs, validates, and documents itself.

The payoff is the audit trail: she approves something she watched get built, including her own correction, and walks away with clean partitioned Parquet plus a generated data dictionary in minutes. For PII-bearing data, "a named person reviewed and approved this exact transform, and here's the report" beats "an agent cleaned it" every time.

Improvements I'd make to the workflow

1

Interrupt mid-step, don't only pause between

Let a chat message cut in while an agent is working: finish the current tool call, then re-plan — with a visible "steering applied" marker. Pause-only-between-steps is the safe MVP; true interruption is the better feel.

2

Turn corrections into durable preferences

Every correction becomes a chip in the rail and a row in AgentCore Memory — so next week's file from the same vendor starts with "email = non-PII" already applied, not re-asked.

3

Always show a diff when a preference changes the plan

Prove the correction changed the output — a before/after on the transform list. If a note can't produce a diff, it was decorative; don't present it as interactive.

4

Tag inferences with confidence, ask before drafting

Mark low-confidence guesses ("email looks like PII — medium confidence") and raise the quick-select question before the script is written, so a wrong guess never reaches the gate.

5

Make the approval card decision-grade

Add an impact preview — rows affected, rows dropped/quarantined, DPU/cost estimate — plus an explicit "what it won't do." That's what keeps approval from decaying into a rubber stamp.

6

Keep a graceful fallback mode

Live steering is the highest-uncertainty part. Ship an "answer a few questions upfront, then run" mode first so there's always a working path if the interactive layer runs long.

Phase 0

Setup & scaffold

Get the account, tools, and an empty deployable agent working before touching data. Ends when a "hello" agent runs locally and answers.

  1. 0.1

    Confirm the toolbox & model access

    Local tooling plus access to the AWS data services.

    • AWS creds for us-west-2; uv, Node 20+, agentcore CLI installed
    • Bedrock model access enabled for your Claude model (the one model/load.py loads)
    • Permissions to create Glue, Athena, S3, and IAM resources
    Test gate

    aws sts get-caller-identity returns your account; agentcore --version works; Bedrock console shows the model as Access granted.

  2. 0.2

    Scaffold a fresh AgentCore project

    A clean project from the AgentCore CLI; nothing is copied from earlier weeks. --skip-git because Project/ already lives inside a git repo.

    agentcore create --project-name EtlCopilot --name EtlCopilot   --framework Strands --model-provider Bedrock --build CodeZip   --language Python --protocol HTTP --memory none --skip-git
    • Pin region_name="us-west-2" in model/load.py; the template sets none and falls back to the CLI default
    • Model: us.anthropic.claude-sonnet-4-6, overridable via ETL_COPILOT_MODEL_ID
    • Fill aws-targets.json (it is generated empty) and set runtimeVersion to PYTHON_3_12 to match the local venv
    • Remove the template's third-party MCP client (mcp.exa.ai web search)
    Test gate

    agentcore validate prints Valid.

  3. 0.3

    Prove the empty agent answers

    Run it locally before adding complexity. agentcore dev deploys to AWS before starting unless you pass --skip-deploy, and agentcore invoke only targets a deployed agent.

    agentcore dev --port 8081 --logs --skip-deploy    # terminal 1
agentcore dev --port 8081 "hello"                 # terminal 2
    Windows

    Pass callback_handler=None to the Agent: the default handler prints every token to a cp1252 console and crashes on emoji. Hot-reload can also miss edits, so restart the server after code changes and make sure port 8081 is free after stopping it.

    Test gate

    The prompt returns a streamed reply from Sonnet 4.6, including non-ASCII characters, with no errors in the dev log.

Phase 1

The data plumbing — no agent yet

Build and run the whole pipeline by hand on dataset 1. You must know exactly what "correct" looks like before any LLM writes a line of ETL. Every piece here becomes a tool the agent calls later.

  1. 1.1

    S3 bucket + landing/staging prefixes + dataset 1

    Separate prefixes so the agent never writes over raw input.

    aws s3 mb s3://<acct>-etl-copilot-uswest2 --region us-west-2
# prefixes: landing/  staging/  scripts/  reports/
aws s3 cp dataset1.csv s3://<acct>-etl-copilot-uswest2/landing/dataset1/
    • Dataset 1 = small (≈50–500 rows) but with one real quirk, e.g. dates as both DD/MM/YYYY and YYYY-MM-DD
    Test gate

    aws s3 ls s3://…/landing/dataset1/ shows the CSV.

  2. 1.2

    Glue crawler → Data Catalog (CSV-locked)

    Point a crawler at landing/. Pin a CSV classifier so the pipeline is CSV-only by construction — this is where your "no PDF/JSON" scope becomes a hard guarantee, not a hope.

    Test gate

    aws glue get-table shows the inferred columns and types for dataset 1.

  3. 1.3

    Glue Data Quality — initial profile

    Run a Data Quality profile / rule recommendation on the catalog table to get null rates, types, and cardinality.

    Test gate

    You can pull the DQ result (nulls %, distinct counts) as JSON — this is the exact payload the Profiler will later read.

  4. 1.4

    Hand-write ONE Python Shell ETL script

    You write this, not the LLM. pandas-based: parse the mixed dates, coerce nulls, mask the PII column, write partitioned Parquet to staging/.

    aws glue create-job --name etl-copilot-job \
  --command '{"Name":"pythonshell","PythonVersion":"3.9",
    "ScriptLocation":"s3://…/scripts/etl.py"}' \
  --default-arguments '{"--additional-python-modules":"pandas,pyarrow"}' \
  --role <glue-role-arn>
aws glue start-job-run --job-name etl-copilot-job
    Test gate

    staging/ holds Parquet; you can read it back and the dates are uniform, nulls handled, PII masked. This output is your golden reference.

  5. 1.5

    Athena validation query

    One workgroup, one query that encodes your 3–5 rules against the staging output and returns a pass/fail row you can read.

    -- e.g. must all be 0
SELECT
  count_if(id IS NULL)                     AS null_ids,
  count(*) - count(DISTINCT id)            AS dup_ids,
  count_if(event_date < DATE '2000-01-01') AS bad_dates
FROM staging_dataset1;
    Test gate

    The query runs and returns all-zero (pass) on your golden output. Phase 1 done: the manual pipeline works end to end.

Phase 2

IAM & the tool boundary

Before the agent can touch any of this, lock down what it's allowed to do. This is a one-step phase, but it's the difference between a demo and something you'd trust — and, as your V2 analysis argues, it's the real safety control, not the human's code-reading.

  1. 2.1

    Least-privilege role for the Execution Agent

    The Execution Agent's role should do four things and nothing else.

    • Start / read runs of the one named Glue job (etl-copilot-job)
    • Query the one named Athena workgroup
    • Read landing/, read+write staging//scripts//reports/ — nothing outside this bucket
    • Read the Data Catalog table
    Deny test

    Assume the role and confirm it cannot start a different Glue job or read another bucket. Even a rubber-stamped approval is safe when the blast radius is this small — a careful review is a weak substitute for a role that makes damage impossible.

    Test gate

    Under the role: start-job-run on etl-copilot-job succeeds; the same call on any other job is denied.

Phase 3

The agent, built one loop at a time

Now wrap the proven plumbing in Strands. Test each tool as a plain Python function before letting the LLM call it, then assemble the loop on dataset 1 only. No UI yet — everything here is driven from agentcore invoke.

  1. 3.1

    Wrap the AWS actions as @tools

    boto3 inside @tool functions, each does one thing and returns a string the agent can read.

    @tool
def start_glue_job(job_name: str) -> str: ...
@tool
def get_job_status(run_id: str) -> str: ...
@tool
def run_athena_validation(table: str) -> str: ...
@tool
def get_dataset_profile(table: str) -> str: ...
    Test gate

    Call each function directly in Python (no LLM). Each returns correct real output against the resources from Phases 1–2.

  2. 3.2

    Script Writer drafts from the profile

    A sub-agent that takes the Profiler summary and produces ETL script text. Draft with Code Interpreter if you want it to self-check syntax; otherwise plain generation is fine to start.

    Test gate

    Feed it dataset 1's profile; the generated script is close to your Phase 1.4 golden script (reads CSV, fixes the same dates/nulls/PII).

  3. 3.3

    The human approval gate

    The Execution Agent presents the draft and blocks until an explicit human approval before calling start_glue_job. Make it two-layer: a plain-English summary is the real decision surface, with the full script collapsed for spot-checks — nobody reviews generated code line-by-line every run, so treating that as the gate makes it a rubber stamp. For now, "approval" is just a follow-up message to agentcore invoke; the UI wraps this later.

    Critical

    Prove the negative first: with no approval, verify the job never starts. Then prove a "deny" halts the run cleanly. Only then test that "approve" lets it run.

    Test gate

    No approval → no start-job-run in CloudTrail. Approve → job runs. Deny → run stops.

  4. 3.4

    The run → validate → revise loop

    On validation fail, feed the specific failing rule back to Script Writer, revise, re-approve, re-run. Seed dataset 1 with a quirk that fails first pass so the loop has to work.

    Test gate

    A deliberately-hard dataset 1 fails validation once, the agent revises, you re-approve, and the second run passes — with re-approval required each cycle.

  5. 3.5

    Supervisor wires it together

    Supervisor holds run state and calls the sub-agents-as-tools (one Agent cached per session, as the template's agent_factory does), with profiling as a step it runs itself for now. This is also where preference-routing will live when the UI arrives — but for now it just sequences the run.

    Test gate

    One agentcore invoke pointing at dataset 1 drives profile → draft → approve → run → validate → pass, end to end, locally. The internal pipeline is now complete for one dataset.

Phase 4

Memory, breadth & evidence

Harden the pipeline: add memory, prove it generalizes beyond dataset 1, produce the docs, and deploy. When this phase is green the whole system works on its own — that is the prerequisite for building any UI.

  1. 4.1

    Add AgentCore Memory

    Store conventions learned this run ("this file's dates are DD/MM"; "email is a SKU, not PII") so the Script Writer reuses them across revisions — and across future runs of the same source — instead of re-deriving.

    agentcore add memory --name EtlCopilotMem   # SEMANTIC / SUMMARIZATION strategy
    Test gate

    Within a run, a convention learned in the first draft is visibly reused in a later revision (check the trace / logs).

  2. 4.2

    Run datasets 2 and 3

    Different quirks each (a stray "N/A" in a numeric field; a column that's sometimes a list, sometimes a scalar). Record first-run success rate.

    Test gate

    Both run through the same pipeline unchanged; you have a real success/fail number and a note on why anything failed.

  3. 4.3

    Documenter — dictionary + quality report

    From the final schema and profile: a Markdown data dictionary (columns, types, null rates, samples) and a quality report (rules, pass/fail, row counts before/after).

    Test gate

    Both artifacts land in reports/ and match the actual final output for each dataset.

  4. 4.4

    Deploy & capture evidence

    Ship it to Runtime and run the real thing — still headless, via the CLI.

    agentcore deploy
agentcore invoke '{"prompt":"onboard s3://…/landing/dataset2/"}'
agentcore traces list   # grab traces + logs for the writeup
    Test gate

    A deployed run succeeds end to end on all datasets from the CLI. Pipeline complete — only now do you start the UI.

Phase 5 · last

The Console UI

Only start this once Phase 4 is green and the whole pipeline runs end-to-end from a plain agentcore invoke. The UI adds no data-correctness — it's purely the human surface described in the Console design target above: upload-only, autonomous, chat-steerable. Build it in this order; each layer is optional on top of the last.

  1. 5.1

    Upload → trigger

    A CSV-only file input that does a presigned PUT to landing/; the S3 write triggers the run (the same trigger the pipeline already uses). Reject non-CSV on both the client and the presign Lambda.

    Test gate

    Uploading a CSV in the browser starts a run you can see in logs; a non-CSV file is refused before it reaches S3.

  2. 5.2

    Live narration — the activity feed

    Open a stream (WebSocket or poll) to the run and render each agent turn as a plain-language bullet summary as it completes. No step buttons — the user watches, they don't drive.

    Test gate

    A browser upload shows the run self-progressing profile → draft → gate, with per-step bullets that match the trace.

  3. 5.3

    Chat preferences + Supervisor routing

    A persistent chat box; messages go to the Supervisor, which routes to the right sub-agent and revises before the next step. This needs the agent to check for new input between turns — the highest-uncertainty part of the whole build.

    Highest risk

    Build a fallback "answer a few questions upfront, then run" mode first, so you always have a working demo if live steering takes longer than expected.

    Test gate

    Sending "email is a SKU, not PII" mid-run visibly reroutes and the next proposal provably changes (a diff). A note that changes nothing is not shown as "applied".

  4. 5.4

    The approval gate, in the UI

    The two-layer card (plain-English summary + collapsed script) that already reflects the conversation. Approve / Request changes / Reject post back on the same session_id — the entrypoint's _extract_prompt + per-session agent cache in app/EtlCopilot/main.py resume the run.

    Test gate

    From the browser: no approval → no start-job-run; approve → runs; reject → stops. Matches the Phase 3.3 behavior exactly.

  5. 5.5

    Host & record the approver

    Host on S3 + CloudFront (or Amplify); add Cognito so each approval carries a named identity, written into the quality report for the audit trail.

    Test gate

    A deployed URL runs a full onboarding; the generated report shows who approved and when.

Definition of done

What you hand in

01

Working pipeline

Deployed on AgentCore Runtime, driving the full profile → approve → run → validate → revise loop on CSV input — usable headless from the CLI.

02

Cleaned data + versioned script

Partitioned Parquet in staging/ and the approved ETL script for each dataset.

03

Docs per dataset

Markdown data dictionary and quality report generated by the Documenter.

04

The metric + writeup

First-run success rate across the 2–3 datasets, with an honest note on what failed and why.

05

Governance

Least-privilege IAM role plus a recorded human approval for every run — the audit trail that makes it trustworthy.

06

Copilot Console (stretch)

The chat-driven UI from Phase 5: upload a CSV, watch it self-run, steer by chat, approve one plan. Built only after 01–05 are solid.

If time is short

Cut in this order: drop the whole Console UI (the pipeline stands on its own via the CLI), drop the Documenter to a hand-written report, keep Profiler as a Supervisor step, run 2 datasets instead of 3. Never cut: the human approval gate, the least-privilege role, and the run/validate/revise loop — those are the parts that make this a real system.

Verify current Glue Data Quality APIs, Python Shell job limits, and AgentCore Memory / approval-gate patterns against the AWS docs before building each phase — this runbook is grounded in the project brief and the verified Phase 0 setup, not a tested end-to-end setup.
