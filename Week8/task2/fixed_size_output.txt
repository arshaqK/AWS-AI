# AWS Shared Responsibility Model

The AWS Shared Responsibility Model divides security responsibilities between AWS and its customers:

## AWS Responsibility: "Security of the Cloud"
AWS is responsible for protecting the infrastructure that runs all AWS Cloud services, including:
- Hardware, software, networking, and facilities
- Physical and environmental controls
- Infrastructure layer security

## Customer Responsibility: "Security in the Cloud"
Customer responsibilities vary based on the AWS services selected:

**For Infrastructure as a Service (IaaS) like Amazon EC2:**
- Guest operating system management (updates and security patches)
- Application software and utilities installed on instances
- Security group (firewall) configuration
- All necessary security configuration and management tasks

**For Abstracted Services (like Amazon S3 and Amazon DynamoDB):**
- Data management (including encryption options)
- Asset classification
- IAM permissions and access control
- Consulting patching and maintenance documentation

## Shared Controls
Some controls are shared between AWS and customers but in different contexts:
- **Patch management**: AWS applies patches for multi-tenant services; customers must understand notification mechanisms and maintenance windows
- **Configuration management**: AWS maintains infrastructure configuration; customers configure their own guest operating systems, databases, and applications
- **Awareness and training**: AWS trains its employees; customers train their own employees

Understanding this model helps you scope your security responsibilities and identify which mitigations are under your control.

## What Makes Agentic AI Unique

Agentic AI systems introduce architectural dimensions that require specialized design considerations:

1. **Agents reason, not only respond**: A single user request might trigger multiple LLM inference calls, tool invocations, memory retrievals, and inter-agent communications. This creates iterative reasoning loops that add latency, cost, and failure surface—requiring different optimization approaches than traditional request-response patterns.

2. **Agents act autonomously**: Agents invoke tools, modify data, and interact with external systems without explicit human instruction at each step. This autonomy demands purpose-built security controls, permission boundaries, and human oversight patterns.

## Key Design Principles

The lens covers the full spectrum of agentic AI architecture:

- **Foundational infrastructure** supporting agent compute and memory
- **Orchestration patterns** coordinating multi-agent workflows
- **Operational practices** ensuring agents remain reliable, secure, and cost-effective in production

## Use Cases

The architectural principles apply across:
- End users through conversational interfaces
- Internal workflow automation
- Production infrastructure operations alongside human engineers

The AWS Well-Architected Agentic AI Lens provides guidance from agent prototypes through production-grade agent systems, addressing reliability, security, and cost-effectiveness at scale.

**What is AWS Lambda:**

AWS Lambda is a managed serverless compute service that lets you run code without provisioning or managing servers. You pay only for the compute time you consume—there is no charge when your code is not running. Lambda takes care of everything required to run and scale your code with high availability.

**When to use it:**

According to the search results, you should use AWS Lambda for:

- Running code for virtually any type of application or backend service
- Backend services for web and mobile applications
- Event and data processing
- Logging and monitoring
- Internet of Things (IoT) applications
- Building stateless serverless applications that support microservice architectures
- Integrating with Amazon API Gateway to run fully managed REST APIs
- Handling interactions with third-party services or other AWS services for custom workflows

The documents also note that Lambda works well when you can set up your code to automatically run from other AWS services, or call it directly from web or mobile apps. For long-running executions that exceed Lambda's limits, you can use AWS Step Functions to orchestrate workflows across multiple Lambda functions or other compute resources.
